# GLM 对话长时间未完成：代理绕过配置排查与修复

记录日期：2026-10-10。

## 问题现象

浏览器中的知识库查询对话持续显示“执行中”，数分钟没有回答；此前一次请求等待约 28 分钟仍未完成。

本次通过 `aipex-mcp-bridge` 读取 Chrome 中的项目页面，再对照 `logs/gateway.log` 和模型配置进行排查。使用的模型为 `glm-5.3-flash`，接口域名为 `open.bigmodel.cn`。

## 已确认的根因

根目录 `.env` 中的 `NO_PROXY` 和 `no_proxy` 都包含 `open.bigmodel.cn`。这使 Gateway 的 GLM 请求绕过代理，直接连接模型接口；在本次开发环境中，直连会超时，经代理访问则能正常返回。

原模型配置同时设置了：

```yaml
timeout: 600.0
max_retries: 3
```

单次请求可以等待 600 秒，OpenAI SDK 内部还允许额外重试 3 次。因此，仅这一层在连续超时情况下就可能累计约 40 分钟，尚未计入其他阶段及应用层重试。

此前日志中，模型调用开始后，分别在约 10 分钟、20 分钟时出现：

```text
Retrying request to /chat/completions
```

这解释了页面长时间没有回答却仍显示执行中的现象。

## 排查依据

| 检查 | 结果 | 判断 |
| --- | --- | --- |
| 浏览器页面 | 原查询持续显示“执行中” | 确认用户看到的故障现象 |
| Gateway 日志 | 沙箱已成功创建并分配给对话 | 本次请求未卡在沙箱启动阶段 |
| 模型请求日志 | 停留在 `on_chat_model_start`，此前每 600 秒发生 SDK 重试 | 阻塞发生在模型调用阶段 |
| 未携带认证的接口连通性检查 | 经代理返回 HTTP 401；直连超时 | 代理路径可到达接口；401 本身不能证明认证有效 |
| 实际 GLM 适配器的最小请求及较大合成请求 | 使用正常代理路径时约 1 秒收到首个响应 | 模型、认证和适配器可以正常工作 |
| 按启动脚本的 dotenv 加载顺序复现 | 修复前超时，修复后约 0.7–1.2 秒收到首个响应 | 确认代理排除配置是本次故障原因 |

启动方式的差异是排查关键：`scripts/serve.sh` 会将根目录 `.env` 中的值导出到服务环境，覆盖启动 shell 中的同名值。独立测试如果优先使用测试进程已有的环境变量，可能走代理而成功，无法复现 Gateway 的直连超时。

## 实施的修复

### 1. 修正代理排除列表

从 `.env` 的以下两个字段中，分别移除 `open.bigmodel.cn`：

```dotenv
NO_PROXY=...
no_proxy=...
```

保留其余原有地址，尤其是本地和内网服务地址；不要直接清空或整段替换排除列表。两个字段需一起检查，避免大小写字段不一致。

本次保留现有代理设置，让 GLM 接口通过代理访问。

### 2. 缩短 GLM 单次超时并关闭 SDK 内部重试

在根目录 `config.yaml` 中，仅修改 `glm-5.3-flash` 对应模型条目：

```yaml
models:
  # 以下仅展示该条目的相关字段；其余配置保留。
  - name: glm-5.3-flash
    timeout: 60.0
    max_retries: 0
```

这两个字段分别控制单次 HTTP 请求超时和 SDK 内部重试。`max_retries: 0` 不会关闭项目 LLM 中间件的重试；`timeout: 60.0` 也不是整段 Agent 对话的总时限。

本次未修改 Qwen 模型配置或业务代码。

### 3. 停止卡住的请求并重启开发服务

通过浏览器停止原请求，保留对话历史。随后重启开发服务，使更新后的代理环境变量生效：

```bash
bash scripts/serve.sh --restart --dev --daemon --skip-install
```

本次工具执行环境未持续保留该命令创建的后台服务，因此最终改为在持续会话中运行：

```bash
bash scripts/serve.sh --dev --skip-install
```

该命令会持续运行；结束会话或按 `Ctrl+C` 会停止服务。选择后台或前台启动方式后，都应检查实际健康状态，不能仅以启动横幅作为成功依据。

## 验证结果

修复后完成了以下验证：

1. 确认两个代理排除字段均不再包含 `open.bigmodel.cn`，GLM 配置为 `timeout: 60.0`、`max_retries: 0`。
2. 使用项目实际的 `PatchedChatDeepSeek` 适配器，并按启动脚本相同的环境变量优先级调用 GLM，最小请求及合成提示词请求均正常收到首个响应。
3. Gateway `/health` 返回 HTTP 200。
4. 通过 `aipex-mcp-bridge` 在原对话中重新提交“请查询一下可连接的知识库有多少”。
5. 浏览器显示查询用时 **57 秒**并返回回答；Gateway 日志记录对应运行状态为 **`success`**。该轮运行从 18:49:52 开始，于 18:50:49 成功结束。

实际查询包含沙箱冷启动、工具发现及多轮模型调用，因此整轮用时与最小模型请求的首响应时间不同。

本次修改限于本地运行配置，验证采用连通性检查和真实浏览器查询，未执行全量单元测试。

## 后续排查建议

- 遇到对话长时间执行，先根据日志区分沙箱启动、模型调用和工具调用阶段。
- 对比直连与代理路径，并检查 `NO_PROXY`、`no_proxy` 及启动脚本的环境变量加载顺序。
- 最小模型请求成功后，继续验证真实对话的完整流程；仅收到 HTTP 响应或首个流式片段不能证明整轮完成。
- 根据模型延迟设置超时和重试预算，避免 SDK 与应用层重试叠加形成几十分钟的等待。
- 排查配置和日志时只读取必要字段；不要输出凭证、完整环境变量或未脱敏的请求头。

该结论针对本次开发环境。其他环境是否需要代理，应通过连通性验证决定，不应统一要求所有 GLM 请求都走代理。
